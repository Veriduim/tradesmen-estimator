# Accessibility Review — TradesLine UX Draft 2

## Overall verdict

The EXPERIENCE.md "Accessibility Floor" says the right things about the new Signup surface, but the mockup that's supposed to be its composition reference contradicts its own prose in three places (unassociated labels, a non-native submit control, div-based trade chips) — so a builder following the mockup literally would reintroduce the very gaps the prose claims to close. Separately, the draft explicitly leaves the already-logged materials/quantity/wholesaler keyboard-nav and labeling gaps "unchanged" even though trade-scoped content now flows through those exact components, and it introduces one new gap of its own: an irreversible, unconfirmed trade selection that disproportionately affects assistive-tech users. Net: partial close on paper, undermined by the reference artifact, plus one new AT-specific risk from the trade-scoping concept itself.

## Findings

- **critical** Signup form labels are not programmatically associated with their inputs — no `for`/`id` pair and no wrapping (`mockups/signup.html:76-79`, and repeated for every field through line 152). This is the exact gap the Accessibility Floor claims to close ("Every signup field has a real, programmatically-associated `<label>` — do not repeat the existing quantity-input labeling gap") and it's also a regression vs. the app's own current login form, which wraps `<label class="field"><span class="field-label">…</span><input …></label>` (`index.html:32-35`). *Fix:* either wrap each input in its label as `index.html` already does, or add explicit `id`/`for` pairs plus `type`, `name`, and `autocomplete` attributes (all absent from every input in `signup.html`) so the mockup is actually a correct template to copy.

- **critical** The "Sign up" submit control is a `<div class="btn-primary">Sign up</div>` (`mockups/signup.html:106`, `:154`), not a `<button type="submit">`. EXPERIENCE.md's Component Patterns table specifically calls out "Real `<form>` (Enter submits — deliberately avoiding the 'Add material' form-less gap logged in `deferred-work.md`)" — but with no submit button/input anywhere in the form, pressing Enter in a text field will *not* submit (a form needs at least one real submit control for implicit submission to fire), and the div itself has no `role`, `tabindex`, or key handler, so it's also unreachable/unactivatable by keyboard for mouse-free users. *Fix:* change to `<button type="submit" class="btn-primary">Sign up</button>` in the mockup and spec it explicitly in Component Patterns so the builder doesn't copy the div pattern.

- **critical** The trade selector is rendered as four plain `<div class="trade-chip">` elements with no `role`, no underlying `<input type="radio">`/`<select>`, no `tabindex`, and no `aria-checked`/`aria-pressed` (`mockups/signup.html:83-88`, `:130-135`). This directly contradicts the Accessibility Floor line right above it in the same doc: "Trade selector is keyboard-operable and exposes selected state to assistive tech (native `<select>`/radio group, not a div-based click-only picker) — do not repeat the existing wholesaler-row/checkbox keyboard-nav gap." The mockup is the artifact a builder will most likely copy markup from, and it reproduces exactly the pattern the prose forbids. *Fix:* rebuild the mockup's trade group as a native radio group (`<fieldset><legend>What's your trade?</legend>` + `<input type="radio" name="trade" id="trade-plumber" value="plumber"><label for="trade-plumber">Plumber</label>` styled to look like the chips) or a native `<select>`, so the reference markup matches the stated requirement.

- **high** The materials-list quantity-input labeling gap and the wholesaler-option/material-checkbox keyboard-nav gap (both already logged in `deferred-work.md`) are explicitly left untouched by this draft. Component Patterns says of "Materials list + wholesaler row": "Unchanged interaction pattern... Wholesaler names shown are trade-appropriate... mocked data" — with no remediation commitment, even though this build pass is precisely what extends that component to carry new per-trade quantities and wholesaler names for Plumber/Carpenter/General Builder. *Fix:* since this pass is already touching the trade-scoped content in that component, add an explicit line item to close the qty-input label gap (`<label for="qty-{id}" class="sr-only">Quantity</label>` or `aria-label`) and the wholesaler-row/checkbox keyboard gap (native `<input type="radio">`/`role="radio"`+`tabindex` per row) as part of this pass rather than deferring again.

- **high** The toast `aria-live`/`role="status"` fix is spec'd only at the markup-attribute level; it doesn't account for the existing `showToast()` implementation's ordering, which sets `toast.textContent = message` **before** `toast.hidden = false` (`js/app.js:123-127`). Many screen readers only pick up a live-region mutation if the element is already un-hidden (present in the accessibility tree) at the moment the text changes; toggling visibility and text together in this order is a known pattern that silently fails to announce in some SR/browser combinations. EXPERIENCE.md's Accessibility Floor doesn't flag this implementation detail. *Fix:* call out in the spec (or just fix in code) that `toast.hidden` must be cleared before/independently of the text mutation — e.g. keep the toast node always un-hidden and toggle visibility via an opacity/transform class instead of the `hidden` attribute — otherwise adding `role="status" aria-live="polite"` to the markup will look fixed in review but not actually announce anything.

- **high** EXPERIENCE.md says signup errors are associated "via `aria-describedby`, consistent with the existing confirm-modal pattern" (`EXPERIENCE.md:78`). But the closer existing analog — a field-level input error, not a modal — is the current login form's `login-name-error` (`index.html:36`), and that pattern does **not** use `aria-describedby` at all; `handleLogin()` just toggles `.hidden` on the `<p>` with no wiring back to the input (`js/app.js:1104-1110`). A builder pattern-matching off the more obviously analogous existing code (a field error, not the modal) is more likely to copy the unassociated version. *Fix:* name the target pattern more precisely — "unlike the existing `login-name-error`, wire each signup input's `aria-describedby` to its error paragraph's `id`, and add `aria-invalid="true"` while the error is shown" — so there's no ambiguity about which existing pattern to follow.

- **high** DESIGN.md's Do's/Don'ts table states `danger` red is only for "destructive confirmation" and explicitly: "Don't: Use red for anything else (it was previously used ad hoc for the remove button; now formalized)" (`DESIGN.md:119`). The signup mockup then uses that same `danger` (#dc2626) token for form-validation error states — input border, tinted background, and error text (`mockups/signup.html:45-46`, `:136`, `:145-147`) — a different semantic (invalid input vs. destructive action). EXPERIENCE.md's State Patterns table doesn't reconcile this. *Fix:* either extend DESIGN.md's Do/Don't row to explicitly permit `danger` for validation errors too, or introduce a separate semantic (e.g. an `error` token, even if visually identical to `danger`) so the two use cases aren't silently conflated and a future contributor doesn't "correctly" avoid red for validation because the Don't column tells them to.

- **medium** `components.primary-button` (white text on `accent` #0d9488) computes to ≈3.75:1 contrast — below the 4.5:1 WCAG AA threshold for normal-size text (14px/600 weight doesn't qualify as "large text"). This is a pre-existing DESIGN.md token pairing, not new to this draft, but this draft makes it materially more consequential: it's now the single, unavoidable call-to-action on the very first screen a user ever sees (Sign up), where previously it was one of several actions on the login/dashboard screens. *Fix:* darken `accent` for text-on-fill contexts (e.g. a `accent-ink`/`accent-700` token around #0f766e, which computes to ≈4.86:1) or add a text-shadow/weight bump; verify against the primary button specifically since it's now signup's sole path forward.

- **medium** `ink-faint` (#94a3b8) is documented in DESIGN.md as reserved for "metadata & timestamps" (`DESIGN.md:81`, `:15`), but the signup mockup uses it for substantive, must-read copy: the address-purpose hint "We use your address to match you with wholesalers who deliver to you" (`mockups/signup.html:40`, `:99`) and the "Demo signup — nothing is sent anywhere" disclosure (`:60`, `:107`). Computed contrast on white is ≈2.57:1 — fails even the 3:1 large-text minimum, let alone 4.5:1. The Voice and Tone table treats the address-reason line as mandatory, non-optional information ("a stranger asking for a home address needs the 'why'"), so it can't be rendered at metadata-tier contrast. *Fix:* render `.field-hint` and `.note` in `ink-dim` (#64748b, ≈4.76:1) instead of `ink-faint`, or bump `ink-faint` itself since DESIGN.md's own token intent (decorative metadata) is being violated by this usage.

- **medium** No signup input carries `required`, `aria-required`, or `aria-invalid`, and no field is statically marked "(required)" — only the email field is marked "(optional)" (`mockups/signup.html:101-104`), leaving required-ness to be inferred by omission and discovered only reactively after a failed submit. Screen-reader users get no upfront, programmatic signal of which fields are mandatory before they attempt to submit. *Fix:* add `aria-required="true"` (or the native `required` attribute) to name/trade/address/town/Eircode inputs, and toggle `aria-invalid="true"` alongside the existing `.err` class when a field fails validation.

- **medium** The trade selector's question ("What's your trade?") has no `<fieldset>/<legend>` (or `role="radiogroup"` + `aria-labelledby`) grouping it with its four options, in either the mockup or the Accessibility Floor's description ("native `<select>`/radio group" — group semantics unspecified). Without it, a screen-reader user tabbing through four radio buttons hears "Electrician," "Plumber," etc. with no group context connecting them to the question. *Fix:* specify `<fieldset><legend>What's your trade?</legend>` explicitly in the Component Patterns row for Trade selector, not just "radio group."

- **medium** New concern from the trade-scoping concept itself: trade selection is framed as irreversible post-signup ("Selection is not editable after signup in this draft (no profile/settings surface exists yet)," `EXPERIENCE.md:51`), and the only confirmation a user gets that their trade was recorded correctly is inferring it from trade-scoped dashboard content afterward — the signup-success toast text ("Signed up — let's get your first job started," `EXPERIENCE.md:69`) doesn't restate the chosen trade. A sighted user can visually re-check the highlighted chip before submitting; a screen-reader user relying on non-visual confirmation of a selection they can never later correct is taking on asymmetric risk, especially compounded by the div-based, state-silent chip picker flagged above. *Fix:* have the success toast (or an on-dashboard confirmation) explicitly restate the recorded trade, e.g. "Signed up as Plumber — let's get your first job started," giving every user (not just sighted ones checking the chip) an explicit checkpoint before the choice becomes locked.

- **low** `mockups/dashboard-trade-scoped.html` renders job cards and preset cards as plain `<div class="job-card">`/`<div class="preset-card">` (e.g. lines 56, 73-75, 90, 107-109) with no `role`/`tabindex`, whereas the actual live implementation already correctly uses real `<button type="button" class="job-card" data-action="open-job" …>` and `<button type="button" class="preset-card" data-action="create-job" …>` elements (`js/app.js:284`, `:362`) — i.e. this specific gap is already fixed in code but not reflected in the new mockup. Low risk since Component Patterns says this pattern is "unchanged" and points to the real code, but a builder treating the static mockup as ground truth could regress a currently-working pattern. *Fix:* render preset/job cards as `<button>` in the mockup too, purely for consistency with the code it's meant to visually mirror.

- **low** `err-text` (#dc2626 on white) computes to ≈4.83:1 — technically clears the 4.5:1 AA minimum for normal text but with very little headroom; minor rendering/anti-aliasing variance could drop it below threshold in practice. *Fix:* no change required, but if `danger` is darkened for other reasons, verify this pairing stays ≥4.5:1.
